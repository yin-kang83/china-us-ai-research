# 可检验性原则：让项目落地经得起人的检验（2026-11-17）

> 适用：MSVS 多源结构核验、中美 AI 公司分析、软著材料、论文与内容产出。
> 核心：**结论必须能被另一个人独立复核**——看得到来源、算得出过程、复现得了结果、找得到边界。

## 1. 什么叫"经得起人的检验"

| 检验动作 | 要求 | 反例 |
|---|---|---|
| **看得到** | 每个数字/事实有来源（URL/文件名/行号/日期） | 只写"据公开数据" |
| **算得出** | 关键结论给出计算式与输入，第三方能重算 | 只给结论不给过程 |
| **复现得了** | 同输入 + 同版本 → 同输出（脚本/参数/版本可查） | 手工拼数、无版本 |
| **查得到边界** | 标明 unknown/未核验/假设；不把推测写成事实 | 把估计当披露 |
| **有人负责** | 报告有复核人/复核记录；高 stakes 双人复核 | 无人签字 |
| **可被质疑** | 复核队列/反例/风险项单独列出，不藏在正文 | 只报喜不报忧 |

## 2. 三层可检验设计

### 2.1 数据层（Data Ledger）

每条数据记录（JSONL）至少包含：

```json
{
  "id": "D-0001",
  "claim": "中国交建 2026H1 营业收入",
  "value": "333159728",
  "unit": "千元",
  "source_type": "定期报告",
  "source": "[本地资料库]",
  "locator": "第589行（主要会计数据表）",
  "retrieved_at": "2026-11-17",
  "confidence": "L1_EXACT",
  "calc": "直接抽取",
  "review": "待复核/已复核"
}
```

### 2.2 结论层（Claim Registry）

每条结论绑定若干 `D-xxxx` 证据 ID，并写清：

- 依据（哪些数据、哪个计算式）；
- 边界（适用条件、反例、未覆盖项）；
- 状态（已验证 / 判断 / 未知）；
- 复核人、复核日期。

### 2.3 报告层（Reviewable Report）

- 开头：数据来源、时点、版本、生成脚本；
- 正文：结论 + 证据引用 + `unknown` 清单；
- 结尾：边界声明 + 复核记录；
- 附件：数据台账（JSONL）、计算脚本、复核清单。

## 3. 现有体系已落地的部分

| 体系 | 已有人检机制 |
|---|---|
| MSVS（上市公司核验） | 抽取带行号证据；双源验证；`unknown` 复核队列；报告边界声明 |
| 软著材料 | 页眉/页数与申请表一致；MANIFEST 校验；填表速查卡一致性自检；说明书边界章节 |
| 论文/预印本 | 数字核对清单（claims-checklist）；证据包；不虚构声明 |
| 内容产出 | AI 标识；人工复核；来源链接；免责声明 |

## 4. 中美 AI 专题的落实方式

1. 每个公司指标 → Data Ledger 记录（SEC/A-H 文件 + 页码/章节 + 抓取时间）；
2. 每条竞争差异/可持续性判断 → Claim Registry（证据 ID + 反例 + 状态）；
3. 报告附"人检清单"：数据抽查 10%、计算复算、来源可打开、`unknown` 占比；
4. 非上市公司信息单列"公开信息/未审计"，不进入同表比较；
5. 结论一律标"判断/待验证"，不写成"事实"。

## 5. 一句话

**"经得起人的检验"不是加一句免责声明，而是把"来源—计算—结论—边界—复核"五件事写进流程。**
外部工具（FFD/Tushare/LLM）只能加速，不能替代人的复核；任何无法复核的结论，宁可标 `unknown`。
